# Stream Video in a WebView: host-app audit

## 1. What this skill does

It reads the native iOS and Android code that hosts a WebView, and the web page that runs Stream's React video SDK inside it, and reports which of the known WebView failure modes the app is exposed to: a call that dies when the phone locks, audio that stays silent after the user returns, a page that reloads or duplicates itself mid-call, a microphone that can never be unmuted. Each finding names the file and line, says what the user experiences, and gives the fix, with minimal Kotlin and Swift sketches in `references/android-host.md` and `references/ios-host.md`. The checklist is split into what holds for any WebRTC SDK inside a WebView and what is specific to Stream's SDK today.

It will not change any file, run a build, install anything, or make a network request. The tools it uses are Read, Glob and Grep. If a question cannot be answered from the code (a Play Console declaration, an OEM battery setting, behaviour on a specific phone), it says so under "Could not determine" instead of guessing.

**SDK baseline.** Every Stream API this guide names exists in `@stream-io/video-react-sdk` 1.44.1 (which ships `@stream-io/video-client` 1.63.0), and every Stream-specific recommendation was checked against that release's source. The guide does not depend on SDK features that are not released yet. Where a check rests on how the SDK behaves, it says which release we observed it on; treat 1.44.1 as the verified minimum and recheck these rows when you upgrade.

**How these checks were established.** Android: a minimal native WebView host on Android 14, 15 and 16 emulators with system WebView 113, 124 and 133, Stream's React SDK 1.43.x and 1.44.0 in the page, with the background, freeze, network-loss and microphone-denial checks repeated on 1.44.1; no physical Android phone (OEM battery managers can add restrictions the emulators do not show). iOS: a minimal WKWebView host on one iPhone 12 mini running iOS 26, loudspeaker route, with a microphone beside the phone judging "the user hears it", plus a few checks on the iOS Simulator, with React SDK 1.43.x and 1.44.0 in the page and the background-handling checks repeated on 1.44.1. The counts quoted in the checks (runs, samples) are correlated samples from a few runs on these devices, not independent validations. Where an item rests on a platform rule, the public documentation page is named. Nothing here was verified against your app: the audit tells you which of the reproduced host behaviours your code has, and the numbers say what we observed, not what will happen on your users' devices.

> **Scope: not tested, not covered.** Not tested, because they need a person on the device: Siri, incoming phone calls, alarms, Bluetooth and wired route changes, memory-pressure kills of the WebContent process (we killed the process by hand), and any physical Android phone. Not covered by this audit: Wi-Fi to cellular handoff, VPN changes and token refresh while the app is suspended; Android audio focus ownership, ducking and routing; authentication and backend failures. Each of these is a real cause of dropped or silent calls. This audit does not rule them out, and a PASS on every row does not mean the integration is sound against them.

## 3. What to scan

Start by establishing which platforms are present, then locate the integration surface for each. Most checks are absence checks: the failure is a missing override, flag or declaration, not visibly wrong code. The inspection boundary is the set of files you read: a row is FAIL only for a violation demonstrated inside them (the call Activity is in view and starts no service; the manifest you read declares none). When the behaviour could live where you cannot see it (a merged manifest from a library, a wrapper, a dependency, generated code, another repository, a Play Console setting, a backend), the row is NEEDS-REVIEW with the place to look, not FAIL.

### Android

Files: `**/AndroidManifest.xml`; `**/build.gradle*` and `**/gradle.properties` (`targetSdk`, `compileSdk`); every `*.kt` / `*.java` that mentions `WebView`, `WebViewClient`, `WebChromeClient`, `WebViewCompat`; the Activity or Fragment that owns the WebView; any `Service` subclass; the Application class (`onTrimMemory`).

Symbols: `WebView.settings` (`javaScriptEnabled`, `mediaPlaybackRequiresUserGesture`, `domStorageEnabled`); `onPause` / `onResume` / `onStop` / `onStart` / `onDestroy` on the call Activity; `webView.onPause()`, `pauseTimers()`, `resumeTimers()`; `reload()`, `loadUrl(` (where they are called from); `onTrimMemory`; `onRenderProcessGone`; `onReceivedError`, `onReceivedHttpError`, `isForMainFrame`; `onPermissionRequest`, `onPermissionRequestCanceled`, `PermissionRequest.grant` / `.deny`, `RESOURCE_AUDIO_CAPTURE`; `requestPermissions`, `RECORD_AUDIO`, `CAMERA`, `MODIFY_AUDIO_SETTINGS`; `<service android:foregroundServiceType=...>`, `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, `FOREGROUND_SERVICE_MICROPHONE`, `startForegroundService`, `ServiceCompat.startForeground`, `stopService`; `FLAG_KEEP_SCREEN_ON`, `keepScreenOn`; `isBackgroundRestricted`; `android:launchMode`, `FLAG_ACTIVITY_NEW_TASK`, `FLAG_ACTIVITY_MULTIPLE_TASK`, `documentLaunchMode`, `onNewIntent`; `android:configChanges`, `supportsPictureInPicture`, `enterPictureInPictureMode`; `addJavascriptInterface`, `addWebMessageListener` (its origin set, `sourceOrigin`, `isMainFrame`), `evaluateJavascript`; `setOnApplyWindowInsetsListener`, `enableEdgeToEdge`.

### iOS

Symbols: `allowsInlineMediaPlayback`; `mediaTypesRequiringUserActionForPlayback`; `pauseAllMediaPlayback`, `setAllMediaPlaybackSuspended`, `closeAllMediaPresentations`; `webViewWebContentProcessDidTerminate`; `reload()` and `load(` call sites; `AVAudioSession.sharedInstance().setCategory`, `setActive`, `setMode`, `.playback`, `.playAndRecord`, `.voiceChat`, `.defaultToSpeaker`, `.mixWithOthers`; `AVAudioSession.interruptionNotification`, `routeChangeNotification`, `mediaServicesWereResetNotification`; `didEnterBackgroundNotification`, `willEnterForegroundNotification`, `sceneDidEnterBackground`, `sceneWillEnterForeground`; `isIdleTimerDisabled`; `requestMediaCapturePermissionFor`, `WKPermissionDecision`; `AVAudioApplication.requestRecordPermission` / `AVAudioSession.requestRecordPermission`; `userContentController`, `add(_:name:)`, `frameInfo.securityOrigin`, `frameInfo.isMainFrame`, `evaluateJavaScript`; how many places create a `WKWebView` or push the call view controller.

### Wrappers (Capacitor, React Native WebView, other in-app browsers)

The same checks apply; the anchors move into the wrapper's props or config. For `react-native-webview`, read the `<WebView>` props `allowsInlineMediaPlayback`, `mediaPlaybackRequiresUserAction`, `mediaCapturePermissionGrantType`, `onRenderProcessGone`, `onContentProcessDidTerminate`, and whether the component is remounted on navigation. For Capacitor and similar, locate the wrapper's native WebView setup and check its defaults for the installed version only against documentation the user supplied or that is in the repository; do not fetch it and do not assume the defaults. If neither is available, mark the dependent rows NEEDS-REVIEW and name the documentation to consult. The Android foreground service is native code either way and must exist in the host project.

### The web page

Files: wherever `@stream-io/video-react-sdk` or `@stream-io/video-client` is imported; the component that renders the call; the router; any `window.addEventListener` for lifecycle events; `package.json`.

## 4. The checklist

Verdict per row: PASS / FAIL / N/A / NEEDS-REVIEW. Mark N/A only when the platform or feature genuinely does not apply, and say why. Never silently skip a row.

Severity: **Blocker** = the call dies or goes silent without user action in ordinary use (locking the phone, switching apps, a failed image load); **High** = a real stability or audio gap on a common path; **Medium** = hardening that prevents a rarer failure or makes failures diagnosable; **Low** = polish.

### A. Vendor-independent (holds for any WebRTC SDK inside a WebView)

**A1. Android: a foreground service of type `mediaPlayback` (plus `microphone` for anyone who can speak) for the whole call.** Blocker.
*Why:* in our Android 15 and 16 emulator runs, an app without a foreground service lost all network access 5 to 6 seconds after the user locked the phone or switched apps (Android's network policy marked the app's uid as background-blocked); the same cutoff followed an idle screen timeout with nobody touching the phone. The call's WebSockets closed, other participants saw the user leave about 15 s later, and audio took several seconds to return after the user came back. On React SDK 1.44.1 without a service, audio came back 6 to 18 s after the user returned from 32 to 74 s away; after 95 s or more away it took 30 s or longer, or had not come back 40 s after the return (6 of 6 runs). Android 14 did not block the network but froze the backgrounded app after about 4 minutes in another app, which also ends the call. With a `mediaPlayback` service running, none of this happened in any case we tested: background, 8 minutes of screen-off, forced deep Doze, battery saver. A speaker needs the `microphone` type as well: with a playback-only service, Android 15 silenced the speaker's microphone one second after screen-off while the call stayed connected, so everyone heard silence. The timing is an observation on emulators, not a platform rule: we did not find the network cutoff documented as a numbered behaviour change, and real phones with OEM battery managers can differ, so confirm it on the devices your users have. Android's public guidance that a foreground service is what keeps user-visible work alive while the app is not on screen is in the "Foreground services" guide and "Power management restrictions". Foreground service types are mandatory from target SDK 34 ("Foreground service types are required", Android 14 behaviour changes), and the `microphone` type is subject to while-in-use restrictions: it must be started while the app is visible ("Foreground service types" reference). The cached-app freezer is described in AOSP's "Cached apps freezer" page. `mediaPlayback` plus `microphone` is the recipe we tested; `phoneCall` is valid only with a Telecom `ConnectionService`, and the `camera` and `mediaProjection` types for background camera or screen capture are outside this audit.
*Detect:* a `<service>` with `android:foregroundServiceType` containing `mediaPlayback` (and `microphone` if the app lets users unmute); the matching `FOREGROUND_SERVICE_*` permissions; a `startForegroundService` / `ServiceCompat.startForeground` call on the join path that runs while the app is eligible to start a foreground service (call Activity visible, runtime permissions granted), whoever triggers it: a start requested from the page can arrive after the app has gone to the background, where it fails ("Restrictions on starting a foreground service from the background"), so the host checks eligibility at that moment and the join waits, with a timeout, for the service to report that it reached the foreground; failure handling inside the service (`startForeground` can throw there, and a `try` around `startForegroundService` in the Activity does not catch it); a `stopService` on leave; `ActivityManager.isBackgroundRestricted()` checked at join, because a user who set the app's battery usage to Restricted lost the service about a minute into a screen-off in our runs. FAIL if there is no service; FAIL if the type is `phoneCall` without a Telecom `ConnectionService`; NEEDS-REVIEW for the Play Console use-case declaration, which is not in the code.
*Fix:* `references/android-host.md` section 1.

**A2. Keep the screen on while a call is live.** Medium.
*Why:* a WebView keeps the screen on only while a video element is playing. In a cameras-off, no-share stretch the device's normal screen timeout fires. Whether that matters is a product choice: most calling apps keep the screen on during a visible call, an audio-only product may prefer to let it lock. It is not a remedy for A1: without the service, the screen-off that follows the timeout ends the call, and that finding belongs to A1; with the service in place, a locked screen did not end the call in our emulator runs, except under the Restricted battery setting described in A1. Public reference: "Keep the screen on" (Android) and `UIApplication.isIdleTimerDisabled` (iOS). In 1.44.1, Stream's SDK requests a Screen Wake Lock only inside its prebuilt embedded call and livestream components (`@stream-io/video-react-sdk/embedded`), not for a call page built from the SDK's other components or the client directly. A page can request one itself with `navigator.wakeLock.request('screen')`, which resolved in Android WebView 124 and 133; the host flag is still the reliable answer.
*Detect:* first establish whether the product means to keep the screen on during a visible call (most calling apps do; the code, UI copy or the user can tell you). If it deliberately lets the screen lock, N/A with that reason; if the intent is unknown, NEEDS-REVIEW. Otherwise: Android: `window.addFlags(FLAG_KEEP_SCREEN_ON)` or `webView.keepScreenOn = true` applied for the whole call screen, cleared on leave (FAIL if only the lobby sets it). iOS: `isIdleTimerDisabled = true` while the call view is shown.
*Fix:* `references/android-host.md` section 2; `references/ios-host.md` section 3.

**A3. Never reload or recreate the call page as a side effect.** Blocker.
*Why:* every reload drops the user from the call, and a page that joins on load then rejoins: a few seconds of silence for the user, a leave and a join for everyone else. Each of the following was reproduced in our host and each produced exactly that. (a) `reload()` or `loadUrl()` in `onResume` / `onStart` / `viewWillAppear`, which reloads every time the user comes back. (b) Reloading or destroying the WebView in `onTrimMemory` (Android) or on `didReceiveMemoryWarning` (iOS): `TRIM_MEMORY_UI_HIDDEN` arrived about 1 s after every switch to another app in our runs. (c) A "page is hung" watchdog that reloads when the page answers a heartbeat late: the page answers late whenever the OS has paused it. (d) `onReceivedError` that reloads without checking `request.isForMainFrame`: on API 23+ it reports every failed subresource ("WebViewClient.onReceivedError(WebView, WebResourceRequest, WebResourceError)" reference), so a blocked analytics beacon or a failed `fetch` from the SDK during a network blip reloaded the whole call.
*Detect:* every `reload(` / `loadUrl(` / `load(` call site and what triggers it; `onTrimMemory`, `didReceiveMemoryWarning`; timers that `evaluateJavascript` a ping and act on a timeout; Android `onReceivedError` handlers without an `isForMainFrame` check; iOS `didFail navigation` / `didFailProvisionalNavigation` handlers that reload. The iOS callbacks are main-frame navigation callbacks and have no per-frame flag, so the check there is different: no reload on `NSURLErrorCancelled`, on a navigation the host itself started, or in a loop, and retries bounded.
*Fix:* `references/android-host.md` section 3; `references/ios-host.md` section 4. A hung-page check, if wanted, should ask the page for the SDK's calling state, not measure ping latency.

**A4. Android: the call Activity survives configuration changes.** High.
*Why:* an Activity that does not declare a configuration change is destroyed and recreated when it happens ("Handle configuration changes"), and its WebView and the call page go with it. In our runs entering and leaving picture-in-picture, dark mode and font scale each rebuilt an undeclared Activity; peers saw a clean leave and a rejoin about a second later.
*Detect:* `android:configChanges` on the call Activity including at least `orientation|screenSize|smallestScreenSize|screenLayout|uiMode|fontScale|density|keyboard|keyboardHidden|navigation`, and the Activity actually handling them (the same WebView survives `onConfigurationChanged`; no re-creation of the WebView); or the WebView held outside the recreated view hierarchy, which passes as well. Declaring a change only moves the responsibility for handling it into the app. FAIL only when `supportsPictureInPicture="true"` is declared without those declarations and the WebView is not held outside the hierarchy; a missing declaration otherwise is NEEDS-REVIEW, to be tested on the app's devices (PiP, split-screen, dark mode, font scale).
*Fix:* `references/android-host.md` section 3.

**A5. Android: no `pauseTimers()` while a call is live (Blocker); no `WebView.onPause()` on a live call page (Medium).**
*Why:* `pauseTimers()` is process-wide: it pauses JavaScript timers for every WebView in the app ("WebView.pauseTimers()" reference), so a non-call WebView's `pauseTimers()` pauses the call page's timers too. With it in `onPause` and the screen off, media kept arriving in our runs but the call's signalling went quiet; the server dropped the session after about 30 s and audio stopped, with a ~6 s rejoin when the screen came back on. `WebView.onPause()` is a different call: per its reference it is a best-effort pause of extra processing (animations, geolocation) and does not pause JavaScript; we did not reproduce it as a call-killer in our runs. Avoid it on a live call page anyway.
*Detect:* `pauseTimers(` in `onPause` / `onStop` of any Activity without a "not in a call" guard: FAIL, Blocker. `webView.onPause(` on the call WebView without that guard: FAIL, Medium.
*Fix:* `references/android-host.md` section 5.

**A6. One call-screen instance, one page.** High.
*Why:* when a notification or deep link opened a second instance of the call Activity in our runs, both pages stayed in the call as the same user; the hidden one kept playing, so the user heard every speaker twice, slightly offset (it sounds like echo), and appeared twice to everyone else.
*Detect:* Android: `android:launchMode` on the call Activity (`singleTop` or `singleTask`; FAIL for `standard` reachable from a notification, and for `FLAG_ACTIVITY_MULTIPLE_TASK` or `documentLaunchMode`), notification `PendingIntent`s carrying `FLAG_ACTIVITY_SINGLE_TOP` / `CLEAR_TOP`, an `onNewIntent` that routes into the existing page ("Tasks and the back stack"). iOS: how many code paths create a `WKWebView` for the call or push the call view controller; a deep-link handler that pushes a second copy. A call screen that is dismissed must also leave the call, unless the product keeps the call alive in a minimised state by design, in which case one coordinator owns the call and every screen attaches to it instead of joining.
*Fix:* `references/android-host.md` section 6; `references/ios-host.md` section 1.

**A7. Rebuild the WebView when its renderer or content process dies.** High.
*Why:* Android: when the WebView renderer was killed, a host without an `onRenderProcessGone` override crashed entirely (the platform default, "Managing WebView objects: Termination Handling API"); a host that returned `true` without rebuilding showed a white screen with no audio; rebuilding and reloading rejoined the call in about a second. iOS: when the WebContent process dies (what jetsam does under memory pressure), `webViewWebContentProcessDidTerminate` fires within about a second, the view goes blank (white in a default host) and audio stops; a host that reloads there rejoined in about 2 s, a host that does nothing leaves the user on a blank screen while peers see a ghost for about 15 s.
An unconditional reload is not the answer either: it loops on a page that crashes while loading and rejoins a call the user has already left.
*Detect:* Android: `onRenderProcessGone` override that removes and destroys the view, creates a new one and loads the call page, returning `true`. iOS: `webViewWebContentProcessDidTerminate` implemented with `reload()` (or a rebuild). Both gated on native call intent (the user has not hung up), bounded to 3 attempts with backoff, restoring the microphone and camera state from native before the new page joins (a state native code does not know stays off until the user turns it on), then an error screen. FAIL at High for a missing handler; FAIL at Medium for an unbounded or ungated one.
*Fix:* `references/android-host.md` section 4; `references/ios-host.md` section 4.

**A8. Autoplay policy allows inline playback without a gesture.** High.
*Why:* a WebView whose policy requires a user action for playback leaves remote audio paused until the user taps (in our iOS Simulator run, every remote audio element and the shared video); on iOS the `WKWebViewConfiguration` default is `.all` for `mediaTypesRequiringUserActionForPlayback` and `allowsInlineMediaPlayback` is false on iPhone, so video goes full-screen (both in the `WKWebViewConfiguration` reference). On Android the `WebSettings` default for `mediaPlaybackRequiresUserGesture` is true.
*Detect:* iOS: `mediaTypesRequiringUserActionForPlayback = []` and `allowsInlineMediaPlayback = true` on the configuration used to create the call WebView. Android: `settings.mediaPlaybackRequiresUserGesture = false`. Wrappers: the equivalent props.
*Fix:* `references/ios-host.md` section 1; `references/android-host.md` section 7 (settings block).

**A9. Microphone permission: ask natively first, then grant only what the page asked for.** High.
*Why:* Android WebViews ask the host for each web permission request. A common pattern denies the first web request while Android's own runtime dialog is still up, then grants later. In our Android host, on every SDK version we tested up to and including 1.44.1, the SDK kept the permission recorded as denied after one denial and later unmutes never reached the host as a new microphone request, so unmute did nothing until a reload (1.44.1 asks again only if the browser reports a permission change, which the WebView did not). The host must therefore never deny first and ask later. Separately, removing `MODIFY_AUDIO_SETTINGS` from the manifest made the WebView's microphone fail with `NotReadableError` in our host.
*Detect:* Android: `RECORD_AUDIO` (and `CAMERA` if used) requested natively on the lobby or join path before the page can ask; an `onPermissionRequest` that grants `RESOURCE_AUDIO_CAPTURE` / `RESOURCE_VIDEO_CAPTURE` for the call page's exact origin when the runtime permission is held, and otherwise requests the runtime permission and answers the web request after the result; an `onPermissionRequestCanceled` override that forgets the pending request, and no answer to a stale request after the page has navigated; `MODIFY_AUDIO_SETTINGS` in the manifest. iOS: `NSMicrophoneUsageDescription` present; if `requestMediaCapturePermissionFor` is implemented, it grants for the call page's origin (not reproduced in our runs; stated from the `WKUIDelegate` reference).
*Fix:* `references/android-host.md` section 7; `references/ios-host.md` section 5.

**A10. Android 15 edge-to-edge: page controls are not under the system bars.** Medium.
*Why:* at target SDK 35 Android draws the app edge-to-edge ("Android 15 behavior changes: edge-to-edge enforcement"), so the top of the call page sat under the status bar in our host and taps there went to the system; the page's "tap to enable audio" prompt and bottom controls can become untappable.
*Detect:* `targetSdk >= 35` together with either insets applied to the WebView's container (`ViewCompat.setOnApplyWindowInsetsListener`) or the page using `env(safe-area-inset-*)` with the WebView receiving the insets. NEEDS-REVIEW if the page is not in the repository.
*Fix:* `references/android-host.md` section 8.

**A11. iOS: the audio session is configured once, deliberately, and interruptions are observed.** Medium.
*Why:* WebKit manages its own audio session for page media; in our runs a host that set `.playback`, `.playAndRecord` or `.soloAmbient` mid-call made WebKit pause every media element, and Stream's SDK (1.43.x and 1.44.0) resumed them within a second (21 of 21 runs). Treat mid-call category changes as a smell rather than a failure for Stream specifically, but note two real effects: `.playAndRecord` with `.voiceChat` and without `.defaultToSpeaker` routes the call to the earpiece, and `.mixWithOthers` changes how other apps' audio interacts with the call. Interruptions (phone call, Siri, alarm) should at least be observed and logged ("Responding to audio session interruptions"), because the page cannot reliably see an interruption that leaves it visible (in our iOS 26 WKWebView, `navigator.audioSession` reported no state). The `audio` background mode in `UIBackgroundModes` did not change any result in our runs (the call stayed audible for 10 minutes in the background with or without it), but Apple's documented contract for background audio is the mode ("Configuring background execution modes"), so a missing mode is NEEDS-REVIEW, not PASS and not FAIL: confirm on your devices and iOS versions.
*Detect:* `setCategory` call sites and when they run; `interruptionNotification` and `routeChangeNotification` observers; `UIBackgroundModes` in `Info.plist`.
*Fix:* `references/ios-host.md` sections 2 and 6.

**A12. Bridge safety: native actions only on messages from the call page's origin.** Medium.
*Why:* if the page can start the foreground service, change keep-screen-on or reload through a JavaScript bridge, any page loaded in that WebView can too.
*Detect:* Android: an `addJavascriptInterface` object that performs native actions is FAIL, because the receiver cannot tell which frame called it and reading the WebView's current URL does not authenticate the caller (any frame in the WebView can call the injected object); the pass is `WebViewCompat.addWebMessageListener` with an exact origin rule (scheme, host and port) and `isMainFrame` checked on each message. iOS: `WKScriptMessageHandler` methods that compare the full `message.frameInfo.securityOrigin` (`protocol`, `host`, `port`) with the call page's origin and check `frameInfo.isMainFrame`. On both, native actions (start or stop the service, reload, leave) are authorised against native call state; a message from the page is a request, not a command.
*Fix:* `references/android-host.md` section 9; `references/ios-host.md` section 6.

### B. Stream-specific (React SDK 1.44.1)

These follow from how Stream's React SDK plays audio (through `<audio>` elements bound per participant and per audio track, microphone and screen-share audio separately) and manages the client. Each row was checked against the 1.44.1 release; the observations behind them come from 1.43.x, 1.44.0 and, where stated, 1.44.1. B7 lists what 1.44.1 already fixes on the SDK side and what it does not. An SDK release does not remove a host item in section A, and a host fix does not remove the need for the SDK release.

**B1. iOS: do nothing to page media when the app goes to the background; never `pauseAllMediaPlayback` on a call page.** Blocker below React SDK 1.44.1, Medium from 1.44.1.
*Why:* the primary rule is to do nothing. With the app backgrounded for 5 s, 30 s, 2 min and 10 min, with or without the `audio` background mode, the call stayed audible throughout in our runs. A host that called `WKWebView.pauseAllMediaPlayback` on background (a typical "save battery" line) left the call silent after the user came back on 1.43.x and 1.44.0. After a 15 s background it stayed silent in every run, while the page saw nothing wrong (elements playing, packets arriving, levels normal). After 2 minutes, audio came back about 19 s after the return, and only because the SDK rejoined the call. On 1.44.1 the same host kept the call audible during and after the background in every run (iPhone, iOS 26.6, 15 s and 2 min). So the call is silenced on earlier releases, and on 1.44.1 the call does not get the silence the host asked for. Only a product that intends silence in the background should touch page media at all, and then with the pair `setAllMediaPlaybackSuspended(true)` on background and `(false)` on foreground. On 1.44.1 the pair silenced the call in the background, and audio returned about 2 s after the user came back. One case where a product wants that silence is letting another app's audio play: with a host that does nothing, a video started in Safari while the call was in the background could not play, because the SDK took the audio back within about a second each time (1.44.0 and 1.44.1); with the suspend pair it played. The two APIs differ in the `WKWebView` reference: `pauseAllMediaPlayback(completionHandler:)` pauses media and leaves it to the page to resume; `setAllMediaPlaybackSuspended(_:completionHandler:)` suspends and, when lifted, lets playback continue.
*Detect:* `pauseAllMediaPlayback` anywhere reachable while the call page is loaded: FAIL, Blocker when the page runs React SDK below 1.44.1 or its version cannot be determined (say which in the finding), Medium on 1.44.1 or later (in our 1.44.1 runs it did nothing for the call, which was not checked on later releases; it turns harmful again if the page is ever pinned to an older release, and like every row it should be rechecked on upgrade). Re-creating the WebView on background: FAIL, Blocker. `closeAllMediaPresentations` on background: NEEDS-REVIEW at Blocker, because we did not test its effect on a call; name it and ask the team to test it. `setAllMediaPlaybackSuspended(true)` without the matching `(false)` on foreground: FAIL, Blocker. The suspend pair in a product that wants the call audible in the background: FAIL, High, because it silences the background call by design.
*Fix:* `references/ios-host.md` section 2.

**B2. Web: the Stream client and call object live above the call route and survive in-app navigation.** High.
*Why:* a client that is created inside a component that unmounts during a call, or whose creating effect has unstable dependencies, is torn down and recreated whenever that component unmounts and remounts (a route change, a conditionally rendered wrapper, a parent re-render with a new object identity), when its cleanup disconnects the user or leaves the call, as the usual effect pattern does. Each cycle is a leave and a rejoin for everyone. Without such a cleanup the result is no better: a second join for the same user, or a live call that no component owns. The call object has the same problem. React strict mode double-invokes effects in development only; it is not a production finding.
*Detect:* where `new StreamVideoClient(` / `StreamVideoClient.getOrCreateInstance(` and `client.call(` are created and what owns them; the `useEffect` dependency array and cleanup; `disconnectUser()` and `call.leave()` call sites. FAIL when the client or the call object is created in a component that unmounts during a call (the call route itself, a conditional render, a component keyed on changing props) and its cleanup leaves, disconnects, or lets a remount join again, or when `disconnectUser()` runs in the cleanup of a route component that the call is meant to outlive. A stable component that owns the client for the intended call lifetime passes, including a call that is deliberately scoped to a route and ends on an explicit hang-up or a confirmed navigation away; `useMemo` alone is not a failure. A module-level singleton passes only if it is scoped to the user session: `disconnectUser()` on logout or account switch, never shared across users or with server rendering. NEEDS-REVIEW if the page is not in the repository.
*Fix:* keep the client in an app-level store or provider above the call route, one per user session; render `<StreamVideo client={client}>` once near the root and `<StreamCall call={call}>` around the call route; join once, leave on hang-up.

**B3. Web: the page does not leave, disconnect or reload on `visibilitychange` or `freeze`, and on `pagehide` only when the page is really going away.** Blocker for leaving on `visibilitychange` or `freeze`; High or Medium for `pagehide` mistakes.
*Why:* a WebView page is hidden on every app switch and screen lock. The SDK handles visibility itself: in 1.44.1 it re-arms its remote-audio playback recovery once the page is visible again and WebKit no longer reports an interrupted audio session, and it runs its own reconnect. A page handler that calls `leave()`, `disconnectUser()` or `location.reload()` on hidden turns every lock into a dropped call. Per event: never leave on `visibilitychange` or `freeze`. On `pagehide`, check `event.persisted`: true means the page is entering the back/forward cache and may come back, so do not leave; false means the page is unloading (including a host reload), where leaving is acceptable and reloading is not. Leave only on an explicit hang-up or a confirmed navigation away. Expect no teardown event at all when the OS kills the process; in our runs the server removed the participant about 15 s later, so nothing in the page needs to run for that case.
*Detect:* `addEventListener('visibilitychange'` / `'pagehide'` / `'freeze'` / `'beforeunload'` handlers and what they call. A `visibilitychange` or `freeze` handler that leaves, disconnects or reloads is FAIL at Blocker (it drops the call on every lock). A `pagehide` handler that reloads is FAIL at High; one that leaves without checking `event.persisted` is FAIL at Medium.
*Fix:* remove the teardown. If the app wants to stop receiving remote video while hidden, call `call.setIncomingVideoEnabled(false)` on hidden and `call.setIncomingVideoEnabled(true)` on visible; note that this also clears any per-participant resolution preference the page had set.

**B4. Web: autoplay-blocked audio is handled with the SDK's hook and `call.resumeAudio()`.** Medium.
*Why:* even with A8 in place, a browser or wrapper can block autoplay. The SDK exposes `useIsAutoplayBlocked()` and `call.resumeAudio()`, which must be called from a user gesture. In 1.44.1 the SDK also retries blocked audio on any click or key press on the page while audio is blocked, and on iOS it tries to keep a silent audio element playing while the page is visible, so that participants who join later can still autoplay for a listener whose microphone is off. Neither is guaranteed to succeed, and blocking can affect only some participants. The user still has to know that a tap is needed: without a visible prompt they may hear nobody, or only some of the call, and have no reason to touch the screen.
*Detect:* `useIsAutoplayBlocked` (or `call.blockedAudioTracker.autoplayBlocked$` outside React) and a visible button or tap target that calls `call.resumeAudio(`.
*Fix:* add a "Tap to enable audio" element bound to `resumeAudio()`, shown while `useIsAutoplayBlocked()` is true; keep it above the system bars (A10).

**B5. Both: host lifecycle and audio events are recorded where they can be matched to the call.** Medium.
*Why:* the page cannot reliably see an audio interruption that leaves it visible (in our iOS 26 WKWebView, `navigator.audioSession` reported no state), that the host reloaded it after a WebContent or renderer death (A7), or the real OS version (a WKWebView on iOS 26 reports `iPhone OS 18_7` in its user agent). When a user complains, those facts are what separates a host cause from an SDK or network cause. After a join, 1.44.1 records page visibility changes (with how long the page was hidden) and, on Chromium-based WebViews, `freeze` / `resume` in the call's own traces, which are sent to Stream with the call's stats when stats reporting is enabled for the call. The SDK has no API meant for events reported by the host, so the host forwards its events to the page and the page writes them to the app's own logs, together with the call id (`call.cid`) and the local participant's session id (`call.state.localParticipant?.sessionId`), so that both views of the same call can be lined up.
*Detect:* a bridge (`evaluateJavaScript` / `evaluateJavascript` into a known page function, or a `WebMessageListener` / `WKScriptMessageHandler`) that forwards app state (background / foreground), audio interruption began / ended, route changes, WebContent or renderer termination and the reload, and the OS version, each serialised as one JSON object (name, payload, timestamp) and never spliced into JavaScript source as text; a native buffer of the last events replayed when the page reports ready, because an event evaluated into a page that is suspended, not yet loaded or gone is lost; and page code that logs them with timestamps, the call id and the session id.
*Fix:* `references/ios-host.md` section 6; `references/android-host.md` section 9.

**B6. Web: screen sharing is offered only where the WebView can capture the screen.** Low; N/A for a page with no share control.
*Why:* MDN's browser compatibility data (October 2026) lists screen capture (`navigator.mediaDevices.getDisplayMedia`) as unsupported in Android System WebView and supported in WKWebView from iOS 27. Where it is missing, every attempt to start a share fails, and neither `call.screenShare.enable()` nor the prebuilt `ScreenShareButton` checks for it first; without an `onError` prop the button only logs the failure, so the user sees nothing happen. This row is about sending a share; receiving one is ordinary remote video. We have not tested sending a screen share from inside an iOS 27 WKWebView. The audit does not check `contentHint` on the share. Stream's servers ask the SDK to keep a screen share's resolution and let its frame rate drop when bandwidth or CPU runs short, and the SDK applies that as the sender's `degradationPreference`. In Chrome and Safari an explicit `degradationPreference` takes precedence over the one a hint would imply, so a hint (including `motion`) does not change whether resolution or frame rate gives way.
*Detect:* `screenShare.enable(` / `screenShare.toggle(` call sites and `<ScreenShareButton`, and whether the control is rendered only when `typeof navigator.mediaDevices?.getDisplayMedia === 'function'` (after a `typeof navigator !== 'undefined'` check if the page also renders on a server). FAIL at Low when a page that runs in Android WebView, or in WKWebView before iOS 27, shows the control without that check.
*Fix:* render the share control only when `navigator.mediaDevices?.getDisplayMedia` is a function; catch the error from a custom `screenShare.enable()` / `toggle()`, or pass `onError` to `ScreenShareButton`, and tell the user why sharing did not start.

**B7. Web: the page runs React SDK 1.44.1 or later.** Medium.
*Why:* 1.44.1 carries client fixes that matter inside a WebView. After a fast reconnect that the server did not resume, the client now switches to a full rejoin on its next attempt instead of waiting out the join timeout: in our Android runs with a forced 30 to 120 s freeze, audio came back 2.7 to 3.5 s after the thaw on 1.44.1, against 7.7 to 8.7 s on 1.44.0 with the same server. On a rejoin the client now listens for the server's subscriber offer before flushing the old connection's stats, which fixes a race that could drop the offer; the client no longer reconnects while the call is leaving; remote audio elements stay mounted across a remote mute and unmute; and the iOS silent element and tap-to-resume from B4. In our iOS runs on 1.44.1, the call also kept playing through a host's `pauseAllMediaPlayback` (B1), which silenced it on 1.44.0. Earlier releases added recovery of remote playback after media interruptions (1.43.4) stopped the endless rejoin loop when ICE never connects (1.43.3), and gave up on devices that gather no ICE candidates (1.44.0). Some WebView behaviours are not fixed as of 1.44.1, and the host items cover them where a host can: slow audio return after the app was in the background without a foreground service (A1), and no second microphone request after one denial (A9). One more has no host fix we know of: after a stale browser `offline` event on a working network, the call stayed in its offline state for as long as we watched (2 minutes on 1.44.1, up to 7 minutes on earlier releases) while audio kept flowing, and a reload recovered it; if your users report a call stuck as offline, tell Stream.
*Detect:* the resolved `@stream-io/video-react-sdk` version in the lockfile (`package.json` alone may hold only a range; do not run `npm`). Below 1.44.1: FAIL at Medium. NEEDS-REVIEW if the page and its lockfile are not in the repository and the user did not state the version.
*Fix:* upgrade to 1.44.1 or later. For the team, not the agent: on each later upgrade, read the release notes for WebView-related entries and recheck the Stream-specific rows.

Produce the report in this order.

**Findings table.** One row per FAIL or NEEDS-REVIEW (per platform when a check fails on more than one), Blockers first:

|---|---|---|---|---|---|---|---|

Verdict is FAIL (a violation shown in the files read) or NEEDS-REVIEW (could not be settled from them; severity then describes the impact if it turns out to be a failure). Platform is Android, iOS, Web or Wrapper. File:line points at the evidence, or at where the missing code should live, marked "not found". **Rows that passed.** A compact list of PASS rows (id and one line of evidence), so the reader sees what was checked, not only what failed.

**Rows not applicable.** N/A rows with the reason (a page with no share control for B6, a platform the product does not ship, that the user excluded from the audit or said is audited separately (a platform that is in scope but whose code is not available is NEEDS-REVIEW), a product that keeps calls alive in a minimised state for the dismissal clause of A6).

**Leave unchanged.** The parts of the integration that are already right, each with a file reference and the check it satisfies. This list may be empty; do not fill it to be polite. It tells the team what not to touch.

**Could not determine.** Everything the code did not answer: Play Console foreground-service declarations, OEM battery behaviour on the devices in use, wrapper defaults for the installed version, the web page if it lives elsewhere, anything that needs a device test. Each with the question a person should answer and how.

Close with one paragraph stating that the audit read code only, which directories and files were read (the actual coverage, not the estimate in section 2) and what was out of reach, and the SDK version assumed.
